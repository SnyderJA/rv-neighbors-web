Workflow Cheat Sheet

Everyday loop: branch, code, review, PR into dev. Production (main) is touched only at release.

The loop — every piece of work

  1. 1
    Get the latest dev
    So you're not building on stale code.
  2. 2
    Make a branch
    A private copy. Nothing here affects dev until you merge.
  3. 3
    Write the code
    The part we do together.
  4. 4
    Run the tests
  5. 5
    Update the three tracker files
    Not optional — a hook blocks the commit without them.
  6. 6
    Commit
    Commit often. Small commits are easy to undo.
  7. 7
    Review before anyone else sees it
    Fix what it flags, commit again, repeat until clean. Add /security-review for Phase 5A work.
    /code-review
  8. 8
    Push the branch
  9. 9
    Open a PR into dev
    Listing tickets in the body is how code links back to the tracker.
  10. 10
    Merge and clean up
    --squash collapses work-in-progress commits into one clean commit on dev.

.claude/SESSION_LOG.md what happened, what's next
.claude/plans/MASTER_PLAN.md phase statuses
.claude/progress.json regenerate — never hand-edit

not_started→ in_progress→ complete

Naming

Branches — phase, then what you're doing:

  • 5p/dependency-alignment
  • 5a/rls-hardening
  • 5b/wire-iap-flow
  • 5c/android-device-pass

Tickets — permanent, never renumbered:

  • 5P-T01a task (code change)
  • 5C-G03a gate test (verification)

Group several tickets per branch. Don't open one PR per ticket.

Sync the live dashboard

Both feeds are generated from the Storybloq ledger — never hand-edited.

The second writes the public investor tracker straight into rv-neighbors-web. Commit and push that repo; it redeploys in about a minute.

Public repo — no task detail. The tracker publishes phase-level rollups only. Internal work items stay in Storybloq.

Release — rare

Only when shipping. Merging this is what makes code production; everything before it is safe to break.

Gotchas

Easy to get wrong

  • DB changes live in rv-neighbors-api, but the tracker files stay in rv-neighbors-app — update them there even when the code change is in api.
  • The commit hook only fires for Claude. If you commit in your own terminal it won't stop you forgetting the tracker files.
  • rv-neighbors-web breaks the pattern on purpose — commits go straight to main because that's what Vercel deploys.
  • Ticket IDs won't read in order on screen. Array order is the priority; the ID is just a permanent handle.
  • Never commit .env or hardcode secrets.
  • Don't mark a gate test complete without exercising it on a device — that's exactly how Phases 4 and 5 ended up wrongly marked done.
